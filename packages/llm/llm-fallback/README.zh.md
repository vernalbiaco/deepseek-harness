# `@deepseek-ai/dsh-llm-fallback`

[English](README.md) | 中文

一个函数插件：当前路由的请求以某个已配置 code 失败时，它会让会话故障转移到一份有序的备用提供方／模型路由列表上。它自己不拥有任何路由：主路由就是会话通过模型选择已经解析出的那条路由，因此部署默认值和用户选择都保持权威，插件只负责从那里向前推进游标。游标不具粘性：它会在下一个用户轮次开始时回到主路由，无条件重新探测主路由，即便主路由仍在失败也是如此，且与步骤、请求或已过去的时间无关；轮次中途的 steering（中途引导）不会触发这次重置，因此同一个开启轮次内的故障转移级联不受影响。

```yaml
- name: '@deepseek-ai/dsh-llm-retry'
- name: '@deepseek-ai/dsh-llm-fallback'
  config:
    backups:
      - { provider: deepseek, model: deepseek-v3 }
      - { provider: anthropic, model: claude-opus-5 }
    failoverCodes: [RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT, EMPTY_RESPONSE, AUTH, QUOTA, INVALID_CREDENTIAL, MISSING_CREDENTIAL, NO_ADAPTER]
```

`backups` 是必填项，至少要列出一条路由，且不得重复。`failoverCodes` 可选；一旦出现就不得为空，省略时使用 `src/config.ts` 中的十个 code。schema 会拒绝没有 `backups` 键的配置项，也会拒绝任何取值类型错误的字段，并点名该字段。另有四种错误配置在插件加载时失败：空的 `backups` 列表、重复的备用路由、写出 `failoverCodes` 键却给出空列表，以及 `backups` 和 `failoverCodes` 之外的任何配置键——schemastery 会透传未知键而不是拒绝它们，否则像 `backup:` 这样的拼写错误会在默认值悄无声息地保持不变的情况下顺利加载。

`dsh-llm-fallback` 在采取动作之前总会先委托给 `agent/request-error` waterfall（瀑布式事件）的其余部分，因此在 normal 重试 mode 下，无论它相对 `dsh-llm-retry` 的挂载顺序如何，都能正确组合：同一条路由先耗尽自己的重试预算，只有该预算开始委托后，游标才会移动。always mode 则需要上面给出的顺序：先挂载的 `dsh-llm-retry` 注册为外层监听器，在应用自己那套无上限的同路由重试之前先委托进 `dsh-llm-fallback`，从而让整条链在第一次符合条件的失败上级联；反过来挂载时，always mode 的无上限重试永不让位，整条链也就永远不会推进。`dsh-compaction-basic` 拥有 `CONTEXT_WINDOW_EXCEEDED`，而它默认不在 `failoverCodes` 之内，因此与两种 mode 以任意顺序组合都可以。

## 模型体验

### 模型请求故障转移

#### 模型看到的内容

模型看不到 `llm/fallback` 事件、路由变更或失败的输出。重试轮次会针对新选定的路由，从持久表层历史中重建请求。

#### Token 影响

每次移到备用路由都是一次新的提供方请求，会重复计费输入 token。

#### KV Cache 影响

一次切换会放弃前一个提供方的前缀 cache；备用路由上的第一次请求按完整输入 token 计费。

## 已知限制与暂缓事项

- **语义上的可互换性是断言出来的，不是验证过的**：插件无法证明某条备用路由支持该会话的工具或推理（reasoning）选项；列出较弱模型的部署自行承担这一选择。上下文窗口差异本身已经安全，因为压缩（compaction）每次检查都会依据持久路由重新解析容量。
- **主路由仍在失败期间，每轮次回到主路由的重置都要浪费一次请求**：每个新的用户轮次都会无条件重新探测主路由；仍超出速率限制、或仍持有已被拒绝凭据的主路由会让该请求再次失败，之后游标才会重新推进到可用的备用路由，因此只要主路由一直不可用，这次失败的请求以及它触发的 cache 失效就会每轮次重复一遍。这与上文 `#### KV Cache 影响` 中描述的一次性 cache 代价不同，后者每次切换发生一次，而不是每轮次发生；冷却计时器方案经过考虑后被否决，因为它会让行为依赖时钟，而快照 fixture（测试前置数据）随后就得对该时钟做归一化处理。
- **一次静默的故障转移会改变作答的模型**：持久事件和标头变更让它可见，但两者都不呈现的客户端，无法为模型行为的变化给出任何解释。可见性还是不对称的：移到备用路由会同时产生 `llm/fallback` 和一次 `request/header` 变更，而每轮次回到主路由只产生标头变更，因此靠跟踪 `llm/fallback` 来解释模型变化的客户端，只会看到会话离开主路由，却永远看不到它回来。
- **首次故障转移之后选中的路由会晚一次组装才生效**：插件在 `agent/request` 处暂存一次外部路由变更，并在下一次 `system-prompt/assemble` 时使其生效，而后者每个步骤运行一次，因此携带该选择的那次请求仍然运行在游标已经选定的路由上；被选中的路由服务于下一个步骤，若该选择落在本轮次的最后一个步骤上，则服务于下一个轮次。选择落在某个轮次上、而该轮次的主路由随后失败时，还要多付一次请求，因为故障转移重试会不经重新组装就重新进入同一个步骤，并运行在备用路由上。在该会话第一次故障转移之前，插件根本不主张任何路由，选择会立即到达提供方，因此这项代价只在发生过一次故障转移之后才出现。
- **选中当前正在作答的那条路由永远不会被采纳；选中最近写入过的路由则要等一个轮次**：只有当被委托的路由不属于以下三者中的任何一个时，路由变更才算外部变更：首次故障转移时捕获的主路由、插件最近一次写入的路由，以及游标在本轮次或上一轮次中写入的各条备用路由。前两者是精确的，因为委托的两个来源都只回溯一个步骤——持久标头指向最后一次请求，而路由所有方的选择就是上一个步骤时的该标头——所以携带其中任一者的委托，正是一个没有任何选择的会话本身会产生的请求。轮次标记刻意比这一回溯范围更宽，原因记录在 `src/state.ts` 中。这份宽度的代价是一个轮次：紧接着一次级联的那个轮次中作出的选择会在该轮次被抑制，并在下一个轮次得到服务，因此它能自行恢复。只有选中插件当前正在服务的那条路由，才会被永久丢弃——主路由失败、第一条备用路由正在作答时，用户选中该备用路由后，仍然由它继续提供服务，而模型选择器仍会报告这次选择。链外的路由，或游标从未到达过的备用路由，则会被立即采纳。要让正在作答的备用路由也可被选中，需要一份对该选择的持久记录，这一点已暂缓。
- **重叠的恢复预算会叠加**：重试、压缩与故障转移各自持有自己的限制，因此一个病态轮次在结束前可能消耗「重试次数 × 链长」次请求。
- **always mode 的重试永不让位**，因此把它与故障转移组合起来的部署必须接受已记录的挂载顺序，否则故障转移不可达。
