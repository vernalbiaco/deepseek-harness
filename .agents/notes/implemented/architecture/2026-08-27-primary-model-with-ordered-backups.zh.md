# Agent Note: 主模型与有序备用模型

Status: implemented

[English](2026-08-27-primary-model-with-ordered-backups.md) | 中文

## 问题

一个会话只运行一条显式的提供方／模型路由。当这条路由触发限流并超出其重试窗口、配额耗尽、持有被拒绝的凭据，或者根本未注册时，即便部署还持有其他路由的凭据，而这些路由本可以服务同一个请求，该轮次仍会以终态失败结束。

`dsh-llm-retry` 恢复的是*同一条*路由的暂时性失败，并且按其构造必然重新请求同一个模型，因此在换一个模型就能立即成功的场景下它无能为力：`AUTH`、`QUOTA`、`INVALID_CREDENTIAL`、`MISSING_CREDENTIAL` 和 `NO_ADAPTER` 之所以不在它的默认可重试集合内，正是因为重复请求毫无意义；`RATE_LIMIT` 预算耗尽后的结局也一样。

[LLM（大语言模型）请求的有界恢复](../../implemented/architecture/2026-06-21-bounded-llm-request-recovery.md)说明推迟了故障转移，理由是「没有当前消费方要求自动回退」；而配置了若干可互换模型的部署正是这个消费方。该说明还把重叠恢复分类器的义务交给「引入它们的插件」，本包正是履行这项义务的插件。

## 决策

产品包 `@deepseek-ai/dsh-llm-fallback` 位于 `packages/llm/llm-fallback/`，与 `dsh-llm-retry` 同级，它持有一份有序的备用路由列表，并在当前路由失败时移到下一条。它只通过已记录的扩展点做出贡献，不改动任何既有包。

### 配置

```yaml
- name: '@deepseek-ai/dsh-llm-retry'
- name: '@deepseek-ai/dsh-llm-fallback'
  config:
    backups:
      - { provider: deepseek, model: deepseek-v3 }
      - { provider: anthropic, model: claude-opus-5 }
```

`backups` 是必填的非空列表，元素为 `{ provider, model }` 对；重复的对会导致插件加载失败。主路由刻意不在其中：它就是会话已经通过 `dsh-agent-default-model` 或用户选择解析出的那条路由，因此插件既不会重复记录这一事实，也不会和模型选择器互相冲突。

`failoverCodes` 是可选的、经过校验的列表，默认值为 `[RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT, EMPTY_RESPONSE, AUTH, QUOTA, INVALID_CREDENTIAL, MISSING_CREDENTIAL, NO_ADAPTER]`。`code` 是开放的字符串分类体系，因此列表之外的任何 code（包括 `CONTEXT_WINDOW_EXCEEDED`、`INVALID_REQUEST`、`ABORTED`，以及 `HTTP_503` 这类适配器专用 code）都会被委托下去并保持终态。

配置错误分两层在插件加载时失败。`Config` schema 拒绝没有 `backups` 键的配置项，也拒绝任何取值类型错误的字段，并点名该字段。随后 `resolveConfig` 拒绝空的 `backups` 列表、重复的备用路由、显式给出却为空的 `failoverCodes` 列表，以及 `backups` 和 `failoverCodes` 之外的任何键。之所以需要未知键防护，是因为 schemastery 会放行未知键而不是拒绝它们；没有这道防护，`backup:` 或 `failOverCodes:` 这类拼写错误会顺利加载，运维人员以为生效的是自己设置的配置，实际生效的却是被静默取用的默认值。这与 `dsh-llm-retry` 中的同一道防护一致。

schema 这一层之所以能作用到 `cordis.yml` 配置项，是因为本包没有默认导出：Loader 的 `unwrapExports` 优先取 `.default`，一旦存在默认导出，被挂载的就是裸的 `apply` 函数，`Config` 和 `inject` 也会随之被丢弃（[bug-fix 说明](../bug-fix/2026-08-27-llm-fallback-default-export-drops-namespace.md)）。`failoverCodes` 声明为 `.default(undefined as unknown as string[])`，原因和两层分开的原因相同：schemastery 会把省略的数组填成 `[]`，而 `resolveConfig` 必须仍把省略的列表看作「未给出」，而不是用户有意清空的列表。

### 注册与每个 agent（智能体）的状态

四个监听器都在插件加载时注册到根 context 上，状态以 agent 为键存放在 `WeakMap` 中。三个 `agent/*` 事件携带 `payload.agent`；`system-prompt/assemble` 不携带，它通过 `context.agent` 拿到自己的 agent：`dsh-agent` 把这个字段合并进 `AssembleContext`，并在 `assembleContextFor` 中与 `scope` 一起设置。在根 context 上注册是正确性要求，而不是图省事：`AgentLoop.setupAndPublish` 会先等待 agent 设置完成再发布，而 ApiProxy 正是在这段设置期间装上自己的 `agent/request` 覆盖，因此在 `agent/created` 时安装的监听器注册更晚、在监听器序列中排得更靠后，并在回溯时被覆盖。Cordis 的 waterfall（瀑布式事件）从最外层开始执行，注册时追加到末尾，因此最早注册者胜出。

每个 agent 的状态共七个字段：游标（`0` 表示主路由，`n` 表示 `backups[n - 1]`）、捕获的主路由选择、由外部变更暂存的路由、最近一次写入的路由、本轮次内到达过的最大游标、上一轮次内到达过的最大游标，以及最后一次重置游标的轮次。

### 游标重置

当 `payload.turn` 与上一次重置的轮次不同时，`agent/inbox/claimed` 把游标重置为 `0`。这道轮次防护是必需的，因为该事件在轮次中途的 steering（中途引导）时同样会触发，而中途引导不得在尚未结束的轮次内重新探测刚刚失败的路由。重试轮次不认领消息，因此同一轮次内的故障转移级联不受影响。

### 请求路由

插件在 `system-prompt/assemble` 处把 `provider` 和 `model` 声明为提示词变量，并在 `agent/request` 处重新计算请求路由。它不能把组装时的目标快照下来重复使用：`AgentLoop.step()` 每个步骤只收到一次组装，而 `{ kind: 'retry' }` 动作会在不重新组装的情况下重新进入它的请求循环（`packages/core/agent-loop/src/agent.ts:333-390`），因此快照会把故障转移后的重试送回刚刚失败的那条路由。它也不能复用 `installModelSelection`，因为后者的覆盖是无条件的，而发生过故障转移之后，位于 `0` 的游标并非无所作为。

当游标为 `0` 且会话内尚未发生故障转移时，插件原样返回委托得到的配置。一旦发生过故障转移，游标为 `0` 时就必须主动重新指定捕获的主路由：ApiProxy 的选择会通过 `session.requestHeader()` 回读，而此时请求头记录的是备用路由；不改动请求会把「每轮次重置」静默变成「整个会话粘住」的行为。

重新指定需要一条采纳外部变更的规则，以免覆盖两个轮次之间做出的有意选择；而委托所能支持的判据，只有插件最近写入过什么。两个委托来源都只能回溯一个步骤，再往前就没有了：没有挂载路由所有者时，委托值就是持久请求头，它记录的是上一次请求；有路由所有者时，委托值是 `installModelSelection` 在本步骤组装时快照的选择，也就是上一个步骤结束时的那份请求头。

因此，插件必须在大致这一窗口内认出自己写过的路由，而覆盖这个窗口需要三个标记：捕获的主路由、当前轮次或上一轮次内写入过的备用路由，以及最近一次写入的那条路由；若没有第三个标记，一次提升会把这条路由甩在前两者的覆盖之外。`adoptIfChanged` 说明了每个标记各自覆盖什么。捕获的主路由和最近一次写入是精确的；轮次标记则刻意宽于它们所代表的回溯范围，理由记录在这两个字段自身的文档里。这个宽度换来的是一个轮次的延迟，而不是丢失一次选择：标记会滚动前移，被它压制的选择会在下一个轮次被采纳。若委托指向的路由落在这三个标记之外，例如游标从未到达过的某个备用路由，那它只可能是一次有意的选择。

选中插件最近写入的那条路由，是任何规则都救不回来的一种情况：它产生的请求内容、顺序和插件状态，与完全没有做出选择时一模一样。只拿最近一次写入做比较，会把路由所有者每个步骤都重新指定一次的常驻选择读成一次新的选择，于是把它暂存下来，下一次组装就在轮次中途把游标重置为 `0`，每个步骤都要在正在失败的主路由上白白花掉一个请求。反过来，把这种回读排除在该比较之外，取消掉的则是每轮次的重新探测：在读取请求头的路由所有者之下，故障转移后的重试所回放的那份组装快照早已移到备用路由，于是重试把它暂存下来，下一次组装再把它提升为主路由。要把一次真实选择和一次回读区分开，需要一个委托本身并不携带的信号。

只有落在该窗口之外的路由才会被采纳：插件把它暂存起来，下一次组装将其提升为主路由，并从它开始重启整条链。代价是，首次故障转移之后，选中捕获的主路由或最近一次写入的路由完全不会被采纳，而选中本轮次或上一轮次游标到达过的某个备用路由，则要等到标记滚动越过它之后才生效。选中捕获的主路由不会损失什么，因为每轮次的重置本来就会重新指定它。选中正在服务的那个备用路由则有损失：主路由失败而由 `b1` 应答时，用户选中 `b1` 之后，只要该 agent 还活着，服务它的就一直是 `b1`，而模型选择器仍报告这次选择。仅有的几条出路是：选中游标从未到达过的备用路由、选中更早的轮次级联经过的备用路由、选中链外的路由，以及新建一个 agent。轮次标记是滚动前移而不是累积的；提升不会动尚未结束的轮次的那个标记，因为该轮次在提升之前写过的路由，仍可能在这个轮次内被委托回来。

因此，两个表层（提示词与请求）的一致是有条件的，而不是绝对的。插件从不主动制造分歧：它自己决定更换的路由都会先暂存、在下一次组装时提升，所以提示词和请求始终指向同一个模型。只有在循环自身的重试语义强制要求时才会出现分歧，即步骤中途发现的故障转移会给重试改道，而该步骤的系统提示词此时已经渲染完成；这种分歧在下一次组装时自愈。提示词变量 Agent Note 正好预见了这种情况。

切换到备用路由会丢弃继承而来的 `reasoningEffort`：推理强度的词汇由提供方拥有，目标路由上不一定存在；重新指定主路由时，会恢复与主路由一同捕获的推理强度。这次捕获是兜底值而不是钉死的值，它只持续到下一次指向主路由的委托为止：游标停在备用路由上时，持久请求头记录的是那条备用路由且不携带推理强度，因此没有别的来源能提供本会话的推理强度；而仍然指向主路由的委托会携带当前选择并覆盖捕获的值，当该选择不带推理强度时则把捕获值清空，这与 `installModelSelection` 自身的规则一致：推理强度缺失即恢复提供方默认行为。

推理强度的变更会在观察到它的那次请求中直接应用，而不像路由变更那样先暂存。它不会制造任何表层分歧，因为推理强度不是提示词变量；它也绝不能进入 `promotePending`：游标只以 `provider`／`model` 为键，把推理强度变更当作提升会重启整条链，并把尚未结束的轮次拉回刚刚失败的那条路由。

提升只携带路由，因此它会把捕获的主路由替换成一条不带推理强度的路由。修补方式是在触发提升的那次组装之后的第一个请求上调用 `refreshPrimaryEffort`；它之所以不可观测，完全取决于这两处调用的位置：`AgentLoop.turn()` 会连续执行 `preStep` 和 `step()`，两者之间没有任何请求，而插件的请求监听器会在 `targetFor` 计算路由之前刷新推理强度。把 `refreshPrimaryEffort` 挪到写入之后，每次提升都会丢掉本会话的推理强度。

### 失败处理与组合顺序

`agent/request-error` 监听器先委托，只在拿到 `undefined` 时才行动。下游返回的 `{ kind: 'retry' }` 会原样返回，因此在 normal mode 重试下，同一条路由总是先耗尽预算再发生故障转移，而区分暂时性失败与路由永久性失败也不需要第二份 code 清单：`dsh-llm-retry` 会对预算之内的 code 短路处理，并在预算耗尽或遇到不归自己管的 code 时委托下去，而这正是故障转移应当动作的时机。

先委托也让本插件在 normal mode 下挂载在 `dsh-llm-retry` 之前时仍然正确。always mode 是例外，它把推荐顺序固定下来：always mode 会先委托，再施加自己的无界重试，因此 always mode 下的重试插件必须是外层监听器，即先挂 `dsh-llm-retry`、后挂 `dsh-llm-fallback`，否则故障转移永远不会触发。always mode 也反转了它自己确立的优先级：先咨询下游意味着第一次失败就会让整条链级联，中间没有任何同路由重试；只有整条链耗尽之后，always mode 才会无限重试，而且重试的对象是最后一个备用路由而不是主路由。`dsh-compaction-basic` 负责 `CONTEXT_WINDOW_EXCEEDED`，该 code 不在 `failoverCodes` 内，因此三者对这个 code 可以任意顺序组合。

载荷携带 `provider` 但不携带 `model`，因此故障转移前的路由是在第一次移动之前从 `session.requestHeader()?.config` 捕获的。游标已经位于最后一个备用路由时返回 `undefined`，失败保持终态；这条链不会回绕。

`NO_ADAPTER` 会到达这个监听器：`buildRequest` 容忍 `prepareCall()` 报出该失败，因为 `llm/stream` middleware 可能服务一条未注册的路由；随后 `LlmRuntime` 会按 [LLM 流的终止失败](../../implemented/architecture/2026-07-29-terminal-llm-stream-failures.md)把最终适配器的选择失败规范化为终止 `finish`。

### 持久事件

一个不进入表层的 `SessionEventMap` 成员 `llm/fallback` 携带轮次、步骤、`from` 与 `to` 路由、新的游标，以及 `LlmFailure`。它是读取时必需的，与 `llm/retry` 一致：`Session.append()` 只接受一个 `SurfaceIntent` 参数，因此没有任何写入路径会设置信封的 `ignorable` 标记，而默认行为宁可对未知类型拒绝过头，也不去恢复一个自己读不懂其路由历史的会话。路由变更本身已经是持久的：只要解析出的路由发生变化，循环就会追加 reason 为 `change` 的 `request/header` 以及 `request/context`，这既让切换可重建，也让模型选择器无需新接线就能报告当前生效的备用路由。

单独发布的 `./invariant` 配套模块会检查：每条 `llm/fallback` 指向的都是当前打开的轮次和步骤（步骤在步骤中途的级联期间保持打开，因此已关闭的步骤即为错误）；它的 `from` 路由与当前生效的持久请求头一致；它的 `to` 路由与该步骤关闭前追加的下一条 `request/header` 一致；游标是正整数，且比同一步骤内上一条记录的游标恰好大 1。

向前查验请求头的这项检查会在所属步骤的任一边界处停止生效，即该步骤的 `step/end`，或任何更晚步骤的 `step/start`：路由与当前生效请求头相同的重试不会追加自己的请求头，会让那条记录始终得不到确认；而在重试之前被截断的日志根本不含 `step/end`，恢复后的会话又会在自己的第一条请求头之前追加自己的 `step/start`。链长不是持久的，因此配套模块不会去重复检查 `advance()` 按构造就已保证的上界；那样做意味着每条记录都要记录链长。

## 考虑过的替代方案

- **在 `agent/created` 时按 agent 复用 `installModelSelection`**：不予采纳，有两点原因：它注册在 ApiProxy 设置期安装之后，因而会被覆盖；而且它的无条件覆盖无法表达日志回读所要求的、游标为 `0` 时的重新指定。
- **保留该辅助函数，并用 `prepend: true` 强制其位置**：不予采纳，因为这只修好了顺序这一半；无条件覆盖仍然会让每轮次重置在默认的 ApiProxy 组合下失效。
- **记录一条权威的模型选择事件**：推迟，这也是唯一能让「选中本插件写过的路由」变得可采纳的方案。`RequestHeaderReason` 只有 `'initial' | 'resume' | 'change'`（`packages/core/session/src/types.ts:228`），因此用户选择和本插件自己的写入使用同一个 reason，日志中任何地方都不区分二者。新增一个 `SessionEventMap` 成员可以做到这一点，代价是改动核心包、重新生成 catalog，以及更新两个 SDK 的预期输出。
- **扩展 `installModelSelection` 使其接受一个解析器**：推迟而非拒绝。这能让两个消费方共用一条代码路径，预发布立场也允许改动核心包，但它为一个至今只有本插件才需要的条件判断，扩宽了两个入口点都依赖的一处接口。出现第三个消费方时再重新考虑。
- **包装 `ctx.llm.stream()`，在一次调用内改用另一个模型重新发起请求**：不予采纳，因为原始流无法持久地分隔已经发出的分片，而且这种切换不会产生 `request/header` 事件，破坏「模型可见即须记录」的不变量。
- **把包含主路由在内的完整链写进配置**：不予采纳，因为本插件位于最外层，这样会在每次请求时都覆盖用户手动做出的模型选择，而不只是在失败之后。
- **用冷却计时器回到主路由**：暂不采纳，因为这会让行为依赖时钟，快照 fixture（测试前置数据）随后必须对其做规范化。每轮次的重置已经足够频繁地重新探测主路由，代价是在限流仍然生效期间，每个轮次多出一次失败请求。
- **把 `failover` 放在 `LlmFailure` 上**：有界恢复说明已经拒绝了这一点：适配器报告事实，部署策略决定动作。

## 后果

配置了若干可互换路由的部署，如今在遭遇路由永久性失败时无需运维人员介入即可继续运行，这类失败包括凭据过期、配额耗尽或适配器未注册；而暂时性失败仍会先在同一条路由上耗尽 `dsh-llm-retry` 的预算，游标才会移动。持久的 `llm/fallback` 事件以及与之相伴的 `request/header` 变更，让每一次移动都可重建，并让客户端无需新接线就能报告当前生效的路由。

代价如下。整条链上的语义可互换性由配置断言，而不由插件验证：某个备用路由若缺少会话所需的工具或推理选项，它被选中后只会换一个原因失败。切换总是会放弃失败提供方的前缀缓存，因此不论这次移动的原因是什么，备用路由上的第一次请求都按完整输入 token 计费。重试、压缩（compaction）与故障转移各自持有独立预算，这些预算相加而不共享，因此一个病态轮次在结束前可能发出「重试次数 × 链长」个请求。always mode 只在已记录的挂载顺序下才能组合，即 `dsh-llm-retry` 在 `dsh-llm-fallback` 之前，因为它无界的同路由重试永远不会让位给更晚的监听器；顺序颠倒会让整条链无法到达。此外，一旦发生过故障转移，指向本插件已经写过的路由的模型选择完全不会被采纳，因为它与那次写入被回读的结果无从区分：会话继续服务游标选中的路由，而选择器报告的是用户的选择。

## 测试

`packages/llm/llm-fallback/tests/config.spec.ts` 覆盖 `resolveConfig()`：默认的与显式配置的 `failoverCodes`，对空链、重复路由、显式配置为空的 code 列表和未知键的拒绝，以及接受同一个提供方下的两个模型、分属两个提供方的同一个模型（因为重复检测以提供方与模型的组合为键，而不是以其中任一单独字段为键）。它还固定了解析后的链与调用方路由对象相互分离这一点，以及一个 `Config schema` 用例块，覆盖 `failoverCodes` 的全部三种配置项状态，外加对缺失 `backups` 的点名拒绝。

`tests/state.spec.ts` 覆盖纯游标逻辑，即 `targetFor()`、`adoptIfChanged()`、`advance()`、`resetForTurn()`、`refreshPrimaryEffort()` 和 `promotePending()`，其中包括：`advance()` 的两侧、`targetFor()` 的返回值以及暂存路由上的对象分离；逐个验证的已写入路由压制项，即在任何故障转移发生之前到达的委托、指向捕获的主路由的委托、指向游标正在服务的备用路由的委托、指向更早一次级联写入的备用路由的委托，以及提升把主路由移走之后指向最近一次写入路由的委托；暂存路径，分别取路由的单个字段脱离链、取一个游标从未到达过的备用路由，以及取一个距离写入它的那次级联已过两个轮次边界的备用路由；轮次标记在轮次边界处滚动前移，以及尚未结束的轮次的标记在一次提升后仍然存活；推理强度刷新，分别只让提供方不匹配、只让模型不匹配，以及在故障转移捕获主路由之前推理强度被更新、被清空或被给出；还有防止轮次中途重新探测的轮次防护。

`tests/fallback.spec.ts` 用 mock 的 LLM 路由驱动组装好的插件：限流之后故障转移到第一个备用路由；`AUTH` 上首次失败即故障转移，中间没有任何重试；委托一个不归本插件管的 code；走完整条链直至终态失败；在下一个用户轮次回到主路由，但在轮次中途的 steering 时不回到主路由；优先采用下游的重试而不是故障转移；dispose（资源释放）之后不再发生故障转移；被外部替换的路由推迟到下一个轮次生效；每次请求都重新指定的常驻选择，在尚未结束的轮次的每个步骤都把游标按在备用路由上；未挂载路由所有者时从已稳定的备用路由继续级联；轮次之间更改的推理强度会到达重新指定的主路由，而轮次中途更改的推理强度不会移动游标；读取持久请求头的路由所有者，在一个持续失败的会话的四个轮次中，每个轮次开始时都重新探测主路由；选中该所有者的会话正在服务的备用路由不改变任何行为；选中其游标从未到达过的备用路由、以及选中链外的路由，都会从该路由重启整条链；第 1 个轮次就级联走完整条链，会让之后每个轮次的请求头回放都被压制；一次性的外部路由变更会稳定在被采纳的那条路由上，而不是与它之前写入的路由交替；选中一次旧级联写入的备用路由，会在没有任何委托来源仍然指向它之后到达提供方；被采纳的路由在尚未结束的轮次已经写过备用路由时发生的提升中存活下来；常驻选择跨轮次边界重新指定仍在失败的主路由，而不会把尚未结束的轮次的任何后续步骤拉回该主路由。

`boundaries the ordinary loop rarely exercises` 用例块覆盖普通轮次到不了的路径：在主路由上捕获的推理强度经由备用路由往返一圈后仍然存活；常驻选择携带的推理强度跨两次轮次重置到达重新指定的主路由；在触发提升的组装之后、被提升的路由写入之前的第一个请求上恢复推理强度；针对不携带 agent 的 context 执行的组装；已经中止的信号交由下游策略处理且不动游标；以及在任何请求头存在之前抛出的失败。

`tests/invariant.spec.ts` 用构造出的会话历史检验 `./invariant` 配套模块：格式正确的记录；步骤中途级联经过多个备用路由；一次无关的请求头变更；完整的失败载荷；轮次或步骤越出当前打开范围的记录；`from`／`to` 与持久请求头不匹配，且逐个改变路由的单个字段；轮次与所属打开步骤自身的轮次不一致的记录；游标序列（包括跳号、重复、非正数或带小数的游标）；每个轮次、每个步骤都重新开始的序列；重试不追加自己的请求头、从而让更晚轮次的请求头得不到检查的记录；所属步骤始终未关闭时，同一项检查在更晚步骤的 `step/start` 处停止生效；以及在插件延迟注册、新建会话，和经由 `dsh-session-persistence` 所用的 `sessions.prepare(id, { seed, meta, seedSource: 'persistence' })` 路径恢复的会话上执行校验，该路径是检查已恢复会话记录的唯一途径。

`tests/loader-composition.spec.ts` 通过真实的 Cordis loader 把 `dsh-llm-retry` 和 `dsh-llm-fallback` 一起挂载，证明组合后的链会激活；证明格式错误的配置项会加载失败，包括空的 `backups`、重复路由、未知键、不是列表的 `backups`，以及完全没有 `config:` 块；还证明没有 `dsh-agent` 时该配置项的 fiber 保持 `PENDING` 而不会 apply。最后三项在本包重新获得默认导出时会失败。它还针对一份按 always mode 解析出的提供方策略，在两个方向上固定 always mode 的挂载顺序：`dsh-llm-retry` 在前时，第一次失败就级联到备用路由，中间没有同路由重试；顺序颠倒时则一直重试同一条路由直至其恢复，其间追加 `llm/retry`，永远不会到达整条链。`tests/scaffold.spec.ts` 和 `tests/types.spec.ts` 固定插件名，以及浏览器安全载荷与会话事件之间的身份一致性。

`examples/headless-agent/fallback.cordis.snapshot.yml` 驱动位于 `examples/headless-agent/tests/snapshots/provider-fallback/` 的无密钥 `provider-fallback` 快照，其中的 `tests/fixtures/fallback-snapshot-backend.mjs` 让主路由失败，因此组装后应用的 transcript（文本记录）会显示级联到达某个备用路由并完成该轮次。
